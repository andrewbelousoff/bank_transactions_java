# 🔐 Кастомная Система Аутентификации и Управления Доступом (DRF)

Данный проект реализует собственную (кастомную) систему разграничения прав доступа на основе ресурсной модели управления (на стыке RBAC и ABAC), выполненную в соответствии с требованиями ТЗ. Система не использует стандартные группы и разрешения Django "из коробки".

## 🗄️ Схема и структура управления ограничениями доступа

Для гибкого контроля доступа в базе данных реализованы следующие сущности и связи:

1. **Пользователи (`CustomUser`)**:
   * Содержат базовые данные (email, ФИО, пароль) и флаг `is_active` для мягкого удаления.
   * Каждый пользователь жестко привязан к одной конкретной **Роли** (связь Many-to-One).
2. **Роли (`Role`)**:
   * Справочник ролей в системе (например, `ADMIN`, `USER`, `MANAGER`).
3. **Ресурсы (`Resource`)**:
   * Зарегистрированные в системе изолированные компоненты или бизнес-объекты (например, `cards`, `transactions`, `reports`).
4. **Действия (`Action`)**:
   * Атомарные операции, которые можно совершать над ресурсами (`CREATE`, `READ`, `UPDATE`, `DELETE`).
5. **Правила Доступа (`ResourceRule`)**:
   * Связующая таблица матрицы прав (Мягкая декларативная связь: **Роль ➡️ Ресурс ➡️ Действие**). 
   * Если для роли пользователя в этой таблице существует явная строчка (например, `USER -> cards -> READ`), то доступ разрешается. В противном случае — отклоняется.

## 🛠️ Как работает ядро безопасности (Кастомная логика)

* **Идентификация и Аутентификация (`CustomJWTAuthentication`)**:
  При каждом запросе проверяется подпись JWT-токена в заголовке `Authorization`. Дополнительно проверяется флаг `is_active`. Если пользователь совершил "мягкое удаление", его флаг равен `False` — система выдаст ошибку `401 Unauthorized` и запретит логин.
* **Авторизация (`CustomRulePermission`)**:
  Наш кастомный класс перехватывает запрос к любому контроллеру (View). Он считывает атрибуты `resource_name` и `required_action`, закрепленные за этим контроллером, и делает точечный запрос в таблицу `ResourceRule`.
  * Если пользователя невозможно определить ➡️ Ошибка **401 Unauthorized**.
  * Если пользователь определен, но правила для его роли в БД нет ➡️ Ошибка **403 Forbidden**.
  * Администратор (`ADMIN`) имеет безусловный доступ ко всем ресурсам по умолчанию.

## 🚀 Инструкция по запуску и тестированию

1. **Активация окружения и запуск сервера:**
   ```bash
   source venv/bin/activate
   python manage.py runserver 8080
   ```

2. **Проверка эндпоинтов через curl (в новом окне терминала):**
   * **Логин (Аутентификация):**
     ```bash
     TOKEN=\$(curl -s -X POST http://127.0.0 -H "Content-Type: application/json" -d '{"email": "user@test.com", "password": "password123"}' | grep -o '"access":"[^"]*' | grep -o '[^"]*\$')
     ```
   * **Доступ к вымышленному Mock-объекту (Разрешено, 200 OK):**
     ```bash
     curl -X GET http://127.0.0 -H "Authorization: Bearer \$TOKEN"
     ```
   * **Попытка административного изменения правил (Запрещено, 403 Forbidden):**
     ```bash
     curl -X POST http://127.0.0 -H "Authorization: Bearer \$TOKEN" -H "Content-Type: application/json" -d '{"role": "USER", "resource": "cards", "action": "DELETE"}'
     ```
